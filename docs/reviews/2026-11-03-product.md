# NullLab independent product and demo audit

Reviewed 2026-11-03. Scope: current source, product documents, and primary-source competitor material. No live API calls, deployment, or application edits. Browser visual testing was left to the coordinating agent; findings below describe verified source behavior, not a claimed usability study.

## Assessment

NullLab has a useful, narrow product kernel: help an ML author determine whether a suspect evaluation step inflated a score, then provide the tested change and reproducible evidence. Today it is primarily a specialized local research harness with a replay presentation. It is not yet a general research evaluation platform or a user-facing multi-agent research room.

The largest score weakness is the gap between an impressive result presentation and the effort a new researcher must expend to obtain that result on their own work. The current engineering does not remove the hardest first-use step: converting a real project into the supported case format while preserving its scientific meaning.

## Verified current journey

1. A visitor can open the prepared page, replay a result, inspect intervals and evidence, copy a reviewer note, and download a recorded patch or JSON bundle. There is no user-input/import/new-audit flow in `report/spa.py` or `report/assets/app.js`.
2. To audit personal work, the user must install Python dependencies, create a case folder with `train.py`, `data.csv`, and usually `excerpt.md`, and implement the expected `load`, `feats`, and `claimed_eval` interface. `agent/ci_check.py:35` discovers only this layout. It does not ingest an arbitrary GitHub repository, notebook, PDF, or research question.
3. The free path runs a small rule library. If a rule cannot settle the case, the offline result is `NEEDS_MODEL` or `UNRESOLVED`, unless an existing repository recording is available (`agent/hybrid.py:319`). This is useful but does not provide full research reasoning without an API key.
4. Live model access also requires the separate `battle-station/bs.py` spend gate (`agent/llm.py:17`, `agent/llm.py:48`). A fresh public clone and API key alone are insufficient.
5. The public-facing server can only rerun named bundled cases in mock mode (`app/server.py:99`). The web app does not invoke the live audit.
6. The proposed patch is based on an AST-normalized copy, not a direct patch of the author's formatting-preserved source (`agent/patch_export.py:5`). A researcher must understand and transfer the change back into their project.

## Ranked findings

### P0: resolve the hero's rules exposure before spending further demo effort

The main hero derives from the civil-war prediction case. `report/spa_data.py:254` replaces civil-war strings, source authors, and onset terms, and its `scrub` docstring explicitly cites the hackathon anti-project list. `build()` applies this recursively to the output. The parent planning rules list political/war projects among anti-projects.

This is a substantive eligibility ambiguity, not a naming problem. Auditing a research evaluation is distinguishable from building a war predictor, but the distinction needs the actual event rules or organizer interpretation. Scrubbing the topic cannot establish compliance. It also weakens transparency. Prefer a clearly permissible real-data hero with genuine evaluation evidence; retain truthful provenance for every historical experiment. The coordinator is verifying official rules independently and reports that the owner accepted this risk in the Nov 2 decision log. That acceptance is not organizer confirmation; this review recommends reconsideration, not unilateral removal.

### P1: real user onboarding is the principal Impact and Demo gap

Evidence: `docs/USAGE.md:5`, `README.md:274`, `agent/ci_check.py:35`, `sandbox/run_factorial.py:31`.

The actual import burden is not “upload your research.” It is “port your training/evaluation code into our experiment contract.” This requires technical skill and can introduce differences from the original result. Current documents openly acknowledge that the case is not necessarily the original pipeline.

First improvement: one supported author self-audit workflow, preferably a local sklearn/tabular project, with explicit dataset/target/split mapping, a compatibility preflight, and an original-score reproduction check before any intervention. Unsupported inputs should stop with a precise explanation. A small guided adapter can be more valuable than several additional agents.

Preferred acceptance evidence: a researcher outside the project completes the flow on their own or an independently prepared eligible example; record setup time, assistance required, successful reproduction, final output understanding, and whether they can apply the change. The user has since confirmed no researcher is available. An AI acting as a research professor can conduct an adversarial walkthrough and usability inspection now, but label that internal validation; it supplies no external user, adoption, or hours-saved evidence.

### P1: the demo showcases results more clearly than it showcases use

Evidence: `report/spa.py:42`, `report/assets/app.js:100`, `report/assets/app.js:176`, `app/server.py:99`.

The opening headline talks about reading an AI answer, while the product actually audits an ML evaluation protocol. This can make viewers mistake the application for an LLM answer checker. The page then introduces G7/G8, preregistration clauses, clean twins, intervals, and evidence rings before establishing a recognizable user's action.

Keep the evidence; lead with one user task: “Before you submit this model score, check whether the evaluation earned it.” Show input, plan, tested intervention, measured effect, retained clean control, and exported reviewer evidence. Put experiment IDs and extended caveats in an evidence panel. Record actual supported execution and label any replay clearly. A replay is valuable for dependable inspection, but is not proof a visitor can audit new work.

### P1: the strongest research path is not the default product path

Evidence: `README.md:111` explicitly states the hybrid model path uses the earlier structured-edit planner, and `README.md:112` says the typed DSL is not wired into it. `agent/hybrid.py:180` confirms the separate model path.

Users trying the advertised hybrid command do not receive the latest G9 boundary featured in technical claims. Integrate and verify one supported path before presenting all research variants as one finished platform. Preserve historical run code and results.

### P1: zero outside-user evidence makes Impact largely hypothetical

Evidence: `README.md:160` explicitly says nobody outside the project has used it; `README.md:150` lists several audiences.

The reproducibility problem is documented, but that is evidence for the problem, not demand for this implementation. Paper authors are the best first persona because they possess the data, understand the pipeline, and can run trusted code locally. Reviewers often lack executable artifacts or permission to share confidential submissions. CI teams need a stable integration and coverage semantics. These are different adoption problems.

Pick one primary persona and one end-to-end task. A candid observed usability session is stronger than adding another audience row to the README.

### P1: headline “FALSIFIED” exceeds the product's otherwise careful language

Evidence: `report/assets/app.js:110` hardcodes `FALSIFIED`; `agent/patch_export.py:78` describes the output as a proposed control, not proof the original paper is wrong; `docs/AUDIT-REPORT.md` explains original pipelines and software versions were not rerun.

Use language such as “Measured evaluation inflation in this reproduced case,” with the claim and controlled protocol named. Show the source and what changed beside the number. This protects scientific credibility and avoids implying a full research paper was falsified by a single score difference.

### P2: integration labels can promise more than the artifact delivers

- The page's “Download bundle” saves JSON containing a recording, note, and diff (`report/assets/app.js:190`). The CLI's reproducibility bundle is a ZIP containing rerun code and a manifest. Label these differently.
- The patch download is for normalized source; it should explain this at the point of download, not only in CLI documentation.
- The CI command can exit zero for `NO_RULE_FIRED` or `UNRESOLVED` (`agent/ci_check.py:89`). Written warnings are honest, but a green check is often interpreted as coverage. Consider an explicit coverage policy and an opt-in fail-on-unchecked setting.
- The workflow is described as unverified on GitHub (`docs/DEPLOYMENT.md:12`) and defaults to one bundled clean case (`.github/workflows/nulllab-audit.yml:32`). This is not yet evidence of useful repository-wide CI adoption.

## Positioning and competition

[Popper's official repository](https://github.com/snap-stanford/POPPER) already provides agentic hypothesis testing, an interactive UI, and support for local OpenAI-compatible inference servers. Its [paper](https://arxiv.org/abs/2502.09858) describes agents designing and executing falsification experiments. A generic “agents collaborate to evaluate research” proposition is therefore not a defensible novelty claim by itself.

[Deepchecks' train-test validation documentation](https://docs.deepchecks.com/en/stable/tabular/auto_checks/train_test_validation/index.html) documents checks for index leakage, train-test sample mixing, and date overlap/duplicates. Merely finding common leakage patterns is also established territory.

NullLab's candidate distinction is narrower: attributable evaluation interventions with measured effects, a clean-twin check against false accusations, and a portable reviewer evidence artifact. This is a positioning hypothesis, not proof no competing product has it. The demonstration should make those elements tangible.

## On the proposed research agent room

A visible role panel can help users understand accountability, but agent names and agreement are not evidence. The smallest useful extension is an independent critic that challenges the planner's proposed intervention and missing evidence, followed by a deterministic execution/statistical check. Keep initial analyses independent, record disagreements, bound rounds, and stop unresolved when required evidence is absent. Do not turn lack of agreement into a reason to keep asking until agents agree.

Measure the additional role against the same one-planner baseline at matched budget: fewer false findings, fewer invalid interventions, better coverage, latency, and cost. The general literature/dataset/research-gap room should follow a proven narrow workflow, rather than displacing it close to submission.

## Suggested first work sequence

1. Resolve the permissible hero and exact current claims.
2. Select the author self-audit journey and supported input contract.
3. Make a fresh clone capable of a genuine audit without private battle-station dependencies; retain bounded spending.
4. Connect the verified planner/guard path to that journey, with clear live/rules/replay states.
5. Conduct a fresh-clone adversarial walkthrough now; label it internal AI review. Seek an outside user later when available.
6. Record a short input-to-evidence demonstration; retain the existing detailed results as proof behind it.

This sequence is a recommendation, not an accepted product decision. Under the root idea scorecard, the narrow extension retains a meaningful Meta role on cases rules cannot decide, uses existing assets, and can be demonstrated without a new broad platform. Eligibility remains conditional on the hero decision. Illustrative present-day product-risk ratings: Impact 4–5/10, Demo 4–6/10. These are audit judgments, not predicted official scores. More agents alone does not address either weakness.
